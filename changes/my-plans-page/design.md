# 技术设计：我的计划页

## 已知事实与约束

- 前端 `journey-plan-app` 为 uni-app Vue3 空模板（createSSRApp 入口、Options API），无 package.json/构建脚本，`pages.json` 仅注册一个 Hello 页；`manifest.json` 已存在。
- 后端 `journey-plan-api` 为单文件空 FastAPI 应用，无依赖清单、无测试、无数据模型。
- PRD 第 7 章：前端 uni-app（Vue 3）、后端 FastAPI（Python 3.10+）、数据库 MySQL 8.x（开发期可 SQLite 过渡）、交互设计令牌沿用柠檬黄主题。
- PRD 9.2-6：数据存储于后端 MySQL（本地开发 SQLite），不依赖第三方云同步。
- **产品决策（2026-08-28，DP-3）**：状态系统全面取消——不做 PRD 3.2.2 四态派生、不提供 FR-PL-02 状态筛选；列表仅区分草稿/非草稿。本次实现以此为最高优先级行为约束，冲突处以本决策为准。
- 其余不可违背的既定规则：FR-PL-03 防抖 ≥300ms、FR-WZ-01 名称 2-20 字符去空格、FR-PL-07 删除二次确认。
- `docs/journey-plan-prototype.html`（v5）为已确认的视觉与交互基准：柠檬黄设计令牌（primary #FACC15、bg #FFFBEB、Poppins/Open Sans 字体、圆角卡片、渐变封面、虚线草稿卡片、底部常驻新建按钮、3 Tab 导航）；原型的四态状态角标与筛选 chips 随产品决策取消（仅保留草稿/非草稿区分），其余结构对照实现。原型为内联 SVG 图标与内存数据，落地 uni-app 时需适配（位图 Tab 图标、真实后端数据）。
- 「同一时间仅一个编辑会话」等约束只作用于 Step3 编辑能力，本次无编辑功能，不受影响。

## 目标与非目标

- **目标**：验收基准（随产品决策调整）可执行——卡片列表（草稿/非草稿区分正确）/搜索/空态引导/编辑改名/删除；AC-NAV 3 Tab 可达且默认我的计划；新建入口可创建草稿并回显列表；后端 API 有 pytest 覆盖字段语义、搜索与增删改；`npm run dev:h5` 可启动验证；页面视觉与交互对齐原型 v5（四态部分除外）。
- **非目标**：四态状态派生与状态筛选（已取消）、Step2/Step3 制定流程、FR-PL-06 编辑每日计划、卡片点击进入计划详情、前端分页交互、Tab 位图图标、账号认证与多用户隔离、DayPlan 真实进度数据、Agent AI/天气/地图外部接口。

## 决策（Decisions）

### 决策 1：后端数据访问层使用 SQLAlchemy 2.0 ORM

- **选择**：SQLAlchemy 2.0 ORM + SQLite 开发（`DATABASE_URL` 环境变量切换 MySQL 8.x）。
- **理由**：PRD 要求开发期 SQLite、生产 MySQL；ORM 屏蔽方言差异，模型后续可演进到 Alembic 迁移。
- **替代方案**：原生 SQL（方言差异需手工处理、迁移无工具链）；SQLModel（生态较新，团队不熟悉）。
- **后果**：引入 ORM 依赖与学习成本；方言差异（如 LIKE 大小写）仍需测试验证。

### 决策 2：取消四态状态系统，仅 completed 标志区分草稿/非草稿

- **选择**：plans 表保留 completed 布尔字段（false=草稿、true=非草稿）；接口返回 completed，不返回任何派生状态；不做状态筛选。
- **理由**：产品决策（2026-08-28）明确要求状态系统全面取消、仅区分草稿；实现必须服从该决策，偏离 PRD 3.2.2/FR-PL-02 并在本设计记录。
- **替代方案**：保留四态派生与筛选（违背产品决策）；派生但不筛选（无意义复杂度）。
- **后果**：PRD 验收项 AC-PL-01 中状态筛选部分不再适用（验收基准已在 proposal 调整）；若未来恢复状态系统，需新变更重新引入派生逻辑与筛选 UI。

### 决策 3：搜索在服务端执行

- **选择**：GET /plans 接受 keyword/分页参数，SQL WHERE 过滤（name LIKE %kw%），前端输入防抖 ≥300ms 后发请求。
- **理由**：数据存于后端（9.2-6）且列表需分页，客户端全量过滤在数据增长后失效。
- **替代方案**：客户端拉全量后过滤（分页失效、数据量大不可行）。
- **后果**：每次搜索触发一次请求，需处理防抖与响应竞态（请求序号丢弃过期响应）。

### 决策 4：前端采用 uni-app Vite 工程化

- **选择**：新增 package.json + vite.config.js（@dcloudio/vite-plugin-uni + Vue 3），`npm run dev:h5` 作为开发与验收运行方式。
- **理由**：现有模板为 Vite 结构（main.js + index.html）但缺工程化文件；HBuilderX 手动运行无法命令行化验证。
- **替代方案**：仅 HBuilderX 运行（无法自动化验证）；用 CLI 官方模板重建工程（破坏现有文件结构）。
- **后果**：需安装 node 依赖并锁定版本（见决策 10）；manifest.json/pages.json 保持兼容。

### 决策 5：视觉基准采用原型 v5 设计令牌（四态样式除外）

- **选择**：以 `docs/journey-plan-prototype.html` v5 为视觉基准：uni.scss 落地柠檬黄令牌（primary #FACC15、bg #FFFBEB、card #FFFFFF、muted #FEF9C3、deep #A16207 等）、圆角卡片、虚线草稿卡片、Poppins/Open Sans 字体；非草稿卡片统一使用柠檬渐变封面（原型中按状态区分柠檬/青柠/灰的封面随产品决策合并为单一柠檬渐变，无状态角标）；卡片结构、空态与新建按钮样式均对照原型实现。
- **理由**：用户确认以原型为参照（DP-2）；PRD 7 章要求沿用柠檬黄主题；四态相关样式随产品决策取消。
- **替代方案**：重新设计视觉（违背既定基准，浪费原型成果）。
- **后果**：H5 可复用原型 CSS 思路；跨端（小程序/App）需按 uni-app 语法落地，字体在部分端回退系统字体。

### 决策 6：TabBar 先文字 Tab，图标资源后续补齐

- **选择**：pages.json tabBar 暂不配置 iconPath，仅文字 Tab；高亮样式沿用柠檬黄（选中色 deep #A16207）。
- **理由**：原型 Tab 为内联 SVG（列表/星形/用户图标），uni-app tabBar 只接受位图 iconPath；项目无现成图标资源，避免捏造位图文件。
- **替代方案**：本次生成位图图标（引入资源制作与多端尺寸维护成本）。
- **后果**：视觉上仅文字，与原型有差异；后续版本补图标即可（tabBar 配置兼容）。

### 决策 7：MVP 单用户默认隔离

- **选择**：plans.user_id 字段存在，默认固定为开发用户 id=1；认证模块接入后再按会话用户过滤。
- **理由**：账号体系（FR-ME）是后续变更，本次无登录态。
- **替代方案**：本次实现认证（范围爆炸，违背 DP-0 确认的范围）。
- **后果**：暂不存在多用户隔离；字段已预留，后续迁移成本低。

### 决策 8：草稿数据允许关键字段为空

- **选择**：Step1 仅提交名称；plans.depart_date/return_date/people_count 可为 NULL；卡片对空字段显示占位（「待完善」）。
- **理由**：PRD 流程 Step1 只有命名，Step2 才填写日期/人数；草稿必须在仅命名后即可持久化（支持中途退出保留）。
- **替代方案**：拒绝创建直到 Step2 完成（违背草稿可中途退出保留的规则）。
- **后果**：查询与展示需处理 NULL；草稿判定不依赖日期（completed=false 即草稿）。

### 决策 9：日期字段无时区，天数按日历日派生

- **选择**：depart_date/return_date 为无时区 date 字段；total_days 按「返回日期 − 出发日期 + 1」日历日计算（含首尾，PRD 3.3.1 天数字义）；无「当前日期」判定（四态派生已取消）。
- **理由**：进度展示需要天数；无时区 date 与 MySQL/SQLite 原生 DATE 类型一致，避免时区换算。
- **替代方案**：datetime 字段 + 时区处理（本次无需求）。
- **后果**：日期缺失（草稿）时 total_days 为空，卡片显示占位；未来若恢复四态状态需重新评估时区基准。

### 决策 10：依赖版本锁定策略

- **选择**：后端 requirements.txt 锁定主版本（fastapi 0.115.*、uvicorn 0.30.*、SQLAlchemy 2.0.*、pydantic 2.*、pytest 8.*）；前端 package.json 安装当日 @dcloudio/vite-plugin-uni 3.x 官方最新稳定版与 Vue 3.4+，安装后提交 package-lock.json 固化精确版本。
- **理由**：保证可复现构建，同时避免捏造不存在的精确版本号；uni-app 插件版本随 HBuilderX 发行节奏更新，锁定到 lock 文件即可。
- **替代方案**：不锁定（环境漂移、验收不可复现）；手工写死精确版本（可能与实际发布版本不符）。
- **后果**：主版本升级需人工评估；lock 文件需随依赖变更提交。

### 决策 11：开发期 CORS 放行本地来源

- **选择**：后端 CORSMiddleware 放行本地开发来源（http://localhost:*、http://127.0.0.1:*），供 dev:h5 直连调试；生产收紧为明确域名。
- **理由**：uni-app H5 开发服务器与 FastAPI 不同源，无 CORS 无法联调；生产环境再收紧。
- **替代方案**：前端 vite 代理转发（H5 可行但小程序/App 端不适用，增加双配置）。
- **后果**：开发期任意本地端口可访问 API（仅本地开发风险，可接受）；生产配置项已预留。

### 决策 12：进度字段预留

- **选择**：响应包含 total_days（按出发/返回日期派生，决策 9）与 generated_days（本次恒 0）；卡片按原型展示进度条与「每日计划已生成 X / Y」文案。
- **理由**：PRD 3.3.1 卡片要素包含进度；DayPlan 表在后续 FR-DY 变更才引入。
- **替代方案**：本次不展示进度（违背 3.3.1 卡片要素要求）。
- **后果**：进度暂不反映真实每日计划数，FR-DY 变更接入后替换查询来源即可。

## 风险与验证

- **风险**：SQLite 与 MySQL 行为差异（LIKE 大小写、方言） → **缓解**：查询经 SQLAlchemy 抽象，SQLite 测试覆盖大小写场景，MySQL 阶段人工验证 → **验证证据**：pytest 大小写搜索测试 + 部署 MySQL 后人工验证记录。
- **风险**：前端无自动化 UI 测试 → **缓解**：关键交互以手动验收清单覆盖（验收基准 + AC-NAV），页面结构对照原型 v5 → **验证证据**：dev:h5 手动验收记录。
- **风险**：搜索响应竞态（旧请求晚于新请求返回，覆盖新结果） → **缓解**：前端以请求序号丢弃过期响应 → **验证证据**：快速输入场景手测记录。
- **风险**：uni-app 工程化引入失败（依赖不兼容） → **缓解**：使用官方 @dcloudio/vite-plugin-uni 稳定版本并按决策 10 锁定 → **验证证据**：`npm run dev:h5` 启动成功作为任务完成证明。
- **风险**：原型视觉在 uni-app 端无法完全复刻（字体、渐变、内联 SVG） → **缓解**：优先保证布局结构、颜色令牌与草稿/非草稿样式一致，字体与图标允许端侧回退 → **验证证据**：dev:h5 与原型并排对照记录差异清单。
- **风险**：产品决策与 PRD 存在冲突（状态系统取消），后续需求或验收口径可能反复 → **缓解**：决策已记录于 dp_0_decisions 与 proposal/design，验收基准同步调整 → **验证证据**：DP-3 批准记录；若口径再变按 Escalation 回退 specifying。
